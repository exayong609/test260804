# 反思题

1. 同步链路会把文件大小、数据库延迟和用户请求生命周期绑定，容易超时且难恢复。小文件、低并发、必须原子返回结果时，同步更简单可靠。
2. 处理单元变大能减少调度和数据库往返，但提高内存、超时和重试成本；变小能细化恢复与进度，却增加队列、日志和连接开销。
3. 提升到 50,000 单/分钟时，数据库索引维护和写入通常先成为瓶颈。先用 COPY/临时表合并、分区和连接预算优化，再横向扩 Worker；不能只增加队列消费者。
4. 队列难以保证绝对只投递一次，网络超时后生产者无法判断消息是否被消费。业务幂等能把重复投递从数据事故变为正常重试。
5. 可确定的数据错误应允许成功行先入库并标记部分成功；系统性错误或规则版本错误应整批失败，避免写入语义未知的数据。
6. 错误表只保存脱敏值，完整原文件放在权限受控、短生命周期的对象存储；排障通过 task_id、行号和字段定位，必要时走授权查看原文。
7. Outbox 按创建时间分区，使用 pending/failed 部分索引；sent 数据短期保留后归档到低成本存储，分区级删除避免大事务和膨胀。
8. 规则问题会表现为特定规则版本、字段和映射阶段错误率同时升高，而数据库问题集中在写入耗时、冲突和连接指标。看板按规则版本与阶段聚合即可快速区分。
